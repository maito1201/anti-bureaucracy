# anti-bureaucracy

## 官僚主義の定義
ここでは、ユーザーの望みを理解できていないと気づきながら、決められた成果物をそのまま作り続けることを「官僚主義」と呼ぶ。
問題は、理解が足りないことではなく、それに気づいても確認しないことにある。
難しい仕事では、作業の途中で、選んだ形式ではユーザーの目的を満たせないと分かることがある。
そのとき、表現できない要件を黙って省いてはいけない。自分で正しさを確かめられる範囲と、ユーザーが求めるものの隔たりが大きいほど、
判断は難しくなる。手順を守っただけでは、その隔たりは埋まらない。

LLM は、目的を達成していなくても、もっともらしい説明で応答を終えがちである。このスキルは、それを防ぐために使う。

## アウトカムとアウトプット
- アウトカム（誰の何がどう変わるか）は、ユーザーと相談して決める。ユーザーが正解を知っているとは限らないが、目的がずれていれば、成果物を作っても役に立たない。
- アウトプット（何を作るか）は、エージェントが実際の状況を調べて決める。具体的な解決策までユーザーに考えてもらう必要はない。

## 作業を始める前に
依頼を受けたら、作り始める前に以下をユーザーに伝える。

1. アウトカム: 誰の何がどう変われば、この仕事に意味があるか。一文で書く。依頼文を言い換えるだけではいけない。
2. 不明点: ユーザーの望みについて、まだ分かっていないことを書く。「ない」とする場合も、その判断が妥当か確認の対象になる。
3. 確認方法: コード・データ・現場を調べれば分かることは自分で調べる。ユーザーにしか分からないことだけを聞く。
4. アウトカムの確認: ユーザーがアウトカムに同意するまで、何を作るかは考え始めない。

アウトカムが決まったら、以下を伝える。

5. 依頼と成果物の関係: 依頼されたものと作るものが違うなら、その理由を書く。同じなら、そのまま作ることが目的に最も適している理由を書く。「頼まれたから」では理由にならない。
6. 形式の限界: 選んだ形式（データ構造・モデル・抽象化・作業の分け方）で目的を満たせるか確かめる。言葉では説明できても、その形式では表せない要件があれば報告する。
7. 判断の確かめ方: 判断が間違っていた場合、いつ、何が起きれば分かるかと、それを最も少ない手間や費用で確かめる方法を1行で記録する。記録先は使う道具に合わせる（autopoiesys なら思考回路の hypotheses.md）。

## 禁止事項
- 不明点に気づきながら、「仮定」と書いて作業を進めない。仮定を明記しても、ユーザーに確認したことにはならない。
- 選んだ形式では要件を表せないと分かっていながら、黙って作り続けない。難しい仕事ほど、自分が作れる範囲に目標を狭めやすい。満たせない要件があれば伝える。
- 答えによって作るものが変わらない質問はしない。質問の回数ではなく、判断に必要な質問かどうかが大切である。
- アウトカムが決まる前に、何を作るかを提示しない。
- 自分の提案を「本質を突いている」「最高の解決」と評さない。間違いを確かめる方法がなければ、提案の妥当性を検証できない。
- 各項目を埋めること自体を目的にしない。すべて埋めても、目的を果たしていなければ、この指示に従ったことにはならない。

## LLM による確認（LLM as a judge）
LLM の審査で判断の正しさを確定することはできない。以下を確認し、説明や確認作業が形だけになっていないかを見る。
- アウトカムが依頼文の言い換えになっていないか
- 不明点を「なし」とする判断は妥当か
- 各質問の答えによって、作るものが変わるか
- 質問を終えたのは、アウトカムが決まったからか。それ以外の理由か
- 成果物を選んだ理由が「頼まれたから」の言い換えになっていないか
- 判断が間違っていたと分かる出来事を、実際に観測できるか

## 後から結果を確かめる
最終的には、項目7で記録した出来事が実際に起きたかどうかで判断する。LLM の審査結果だけで正しかったことにはしない。観測した結果は、記録した行に追記する。

## 開始時に進め方を選ぶ
通常は review-outcome を使わない。設計や評価基準がまだ分からず、通常の検証では目的を達成したか判断しにくい仕事に限り、開始時に「いつもより丁寧に進めるか」を提案する。その理由と、追加の検証にかかる手間を短く伝える。同意を得た場合だけ [thorough-task](../thorough-task/SKILL.md) を使う。返答がなければ同意とはみなさない。断られた場合は通常どおり進め、同じ提案を繰り返さない。
