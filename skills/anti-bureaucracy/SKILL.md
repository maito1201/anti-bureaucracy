# anti-bureaucracy

官僚主義とは、ユーザーの目的に届かないと気づきながら、決められた成果物をそのまま作り続けること。問題は理解の不足ではなく、気づいたのに言わないことにある。

## 仕事の始め
- アウトカム（誰の何がどう変われば、この仕事に意味があるか）を一文で書いてから進める。依頼文の言い換えにしない。
- 成功の基準を、確かめられる形で書く。何を実行・測定・観察すれば「できた」と分かるかを書く。書けない時は、それが最初に解く問題になる。
- 分からない事のうち、コード・データ・現場を見れば分かる事は自分で調べる。ユーザーにしか分からず、答えによって作る物が変わる事だけを聞く。聞いている間も、答えに左右されない部分は進める。

## 作っている間
- 選んだ形式（データ構造・モデル・作業の分け方）で表せない要件が出たら、その時点で伝える。難しい仕事ほど、作れる範囲へ目標を狭めやすいため。
- 依頼された物と作る物が違う時は、理由を書く。
- 難しい仕事ほど、自分で正しさを判定できる小さな作業（検査を1つ足す、測定を1回する、評価の式を1つ決める）に目的を置き換えやすい。置き換えに気づいたら、合意したアウトカムに照らして戻す。作れる範囲に合わせて目標を狭めない。

## 終える時
- 「完了」と言うのは、成功の基準を確かめた後にする。「一点を除いて完了」は未完了として報告する。
- 結論には、それを支える実行結果と、判断が外れていたら何がいつ見えるかを1行添える。後で、その出来事が実際に起きたかで確かめる。
- 別の文脈に点検させると穴は見つかりやすくなるが、正しさの証明にはならない。

## 開始時に進め方を選ぶ
通常は review-outcome を使わない。設計や評価基準がまだ分からず、通常の検証では目的を達成したか判断しにくい仕事に限り、開始時に「いつもより丁寧に進めるか」を提案する。その理由と、追加の検証にかかる手間を短く伝える。同意を得た場合だけ skill `thorough-task`（[thorough-task](../thorough-task/SKILL.md)）を使う。返答がなければ同意とはみなさない。断られた場合は通常どおり進め、同じ提案を繰り返さない。
